## lastmod: impact and a concrete, codebase-grounded fix

### Why this matters here specifically
The site's own known-findings context (SITE-CONTEXT.md #1) already flags that blog publishing stalled 22 days ago after a 12-post daily run (2026-10-08 to 2026-10-19). Once that cadence resumes (`docs/15-day-blog-content-calendar.md` plans 15 posts total; 16 are live today per `src/content/blog/`, so the calendar is mid-execution), `lastmod` is the one sitemap field that would let Google's crawler prioritize re-fetching genuinely new/updated posts without waiting for a full re-crawl discovery cycle. Right now the sitemap gives Google no freshness signal at all for a site whose primary growth lever is content publishing cadence — that's a real, not cosmetic, gap.

### The fix already half-exists in the codebase
`src/content/config.ts` already defines `updatedDate: z.string().optional()` on both the `blog` and `guides` collections (lines 9 and 31), and `src/layouts/ArticleLayout.astro` already computes `dateModified: updatedDate ?? publishDate` (lines 51 and 58, used for `BlogPosting`/`Article` JSON-LD) and `modifiedTime={updatedDate ?? publishDate}` (line 74, used for the OpenGraph `article:modified_time` meta tag), plus a visible "Updated {updatedDate}" byline fragment (line 87) when `updatedDate !== publishDate`. In other words: **the exact "last significant change" value the sitemap needs is already computed for every blog/guide page — it's just not being fed into the sitemap too.**

Caveat confirmed by grep across `src/content/`: no `.md` file currently sets `updatedDate` — all 16 blog posts, 3 guides, and the 1 update entry rely on `publishDate` only. That means today `dateModified` already equals `publishDate` everywhere in the existing JSON-LD/OG output too. This is a latent content-ops gap (worth a one-line flag to whoever owns editorial workflow — editors should set `updatedDate` whenever a post gets a real substantive edit, not on every typo fix), not something to fix inside the sitemap itself.

### Recommended implementation
1. **For the 20 content-collection pages (16 blog + 3 guides + 1 update):** add an `@astrojs/sitemap` `serialize(item)` function in `astro.config.mjs` that looks up each URL's slug against a map built from `getCollection('blog')` / `getCollection('guides')` / `getCollection('updates')`, using the same `updatedDate ?? publishDate` logic already in `ArticleLayout.astro` — so the sitemap, the JSON-LD `dateModified`, and the OG `modifiedTime` all stay in sync from one source of truth instead of drifting. `@astrojs/sitemap` v3's `serialize` option supports this; it runs at build time where `astro:content` collections are available.
2. **For the 43 non-collection static pages** (`/about/`, `/terms/`, `/withdrawal/`, the `/games/*` pages, etc.) and the 4 collection hub pages (`/blog/`, `/guides/`, `/updates/`, homepage): these have no frontmatter date at all, so `lastmod` needs a different source. **Do not use filesystem mtime at build/deploy time** — every static build touches every output file's mtime regardless of whether content actually changed, which would stamp all 43 pages with the deploy date on every single deploy (exactly the "all identical lastmod" anti-pattern, and actively misleading since it wouldn't reflect real edits). Instead, derive it from **git commit history** at build time (e.g., `git log -1 --format=%aI -- <source file>` per route), which this audit spot-checked and confirmed reflects genuine content edits, not noise: `src/pages/withdrawal/index.astro` → last touched 2026-08-17 (initial commit, never revised since), while `src/pages/about/index.astro` and `src/pages/terms/index.astro` → last touched 2026-10-04 (the SEO title/description rewrite commit) — i.e., git history already distinguishes "never revised" pages from "recently revised" pages correctly, which is exactly what Google's lastmod guidance asks for.
3. Validate the resulting `<lastmod>` values are W3C-datetime-formatted (`YYYY-MM-DD` or full ISO 8601 with timezone) once implemented — `@astrojs/sitemap` emits whatever string `serialize()` returns, so malformed dates in frontmatter (e.g., a typo'd `publishDate`) would propagate silently.

This is a build-pipeline change, not a copy-only fix — flagging the concrete approach and the exact files involved (`astro.config.mjs`, `src/content/config.ts`'s existing `updatedDate` field, `ArticleLayout.astro`'s existing date logic) for whoever implements it, rather than prescribing exact code.

## Scaling assessment for ongoing blog growth

**No structural change needed.** `@astrojs/sitemap` already outputs the index + sub-sitemap pattern (`sitemap-index.xml` → `sitemap-0.xml`) even at today's trivial scale of 64 URLs, and it automatically shards into additional `sitemap-1.xml`, `sitemap-2.xml`, etc. (updating the index accordingly) once a single file would exceed the 50,000-URL/50MB caps — that threshold-crossing is handled by the integration itself, not something this site's build config needs to pre-empt.

Checked the growth trajectory against `docs/15-day-blog-content-calendar.md` and `docs/content-inventory.md`: the calendar plans 15 blog posts total (1/day cadence via the VPS cron described in SITE-CONTEXT.md #1), 16 are already live, and `docs/content-inventory.md`'s own stated rationale (the `blog` collection is "deliberately scoped to evergreen, general-knowledge topics... rather than an operator 'news' feed" because fabricating news volume "would violate the site's core no-fabrication rule") caps realistic growth to a modest, editorially-constrained pace — nothing close to the tens of thousands of URLs that would force sharding. At even an aggressive sustained 1 post/day for 5 years, that's ~1,825 URLs, still 3.6% of the per-file cap. **Conclusion: the current single-file sitemap structure scales cleanly for the foreseeable content roadmap; revisit only if the site's scope changes materially (e.g., programmatic location/city pages, which this site has none of today).**

## Secondary finding (adjacent, not XML sitemap itself): HTML `/sitemap/` page omits all blog posts

`src/pages/sitemap/index.astro` renders the human-readable sitemap at `/sitemap/`. It explicitly enumerates `getCollection('guides')` (3 articles) and `getCollection('updates')` (1 entry) as their own sections, but has no equivalent section for `getCollection('blog')` — the blog is represented only via the single hub link (`{ label: 'Blog', href: '/blog/' }`) inherited from `FOOTER_NAV` (`src/config/nav.ts` lines 38/88). Net effect: all 16 individual blog post URLs are invisible on the one page whose explicit purpose ("a full, human-readable list of every page on PakRummyOfficial.com," per the page's own `description`) is to list every page. This doesn't affect the XML sitemap's correctness (blog posts are all present there, confirmed above) or crawlability (the `/blog/` hub already links every post), but it's a one-line fix for internal-link redundancy/UX — add a `guides.map`-style section for `getCollection('blog')` alongside the existing guides/updates sections.

## Bottom line

- The XML sitemap itself is structurally clean: valid XML, correctly declared in `robots.txt`, zero coverage drift against the confirmed 64-page crawl, no `priority` bloat, trivial scale relative to all caps, and an index+shard pattern that will auto-scale without intervention.
- The one real defect is the complete absence of `<lastmod>` — not a formatting bug but a missing field, with a fix path that's unusually concrete here because half the machinery (`updatedDate` schema field, `dateModified ?? publishDate` logic) already exists in the codebase for JSON-LD/OG and just needs to be reused in `astro.config.mjs`'s `serialize()` option, paired with a git-history-derived date for the 43 pages that have no frontmatter date at all.
- `changefreq` is harmless but uninformative; safe to delete for cleanliness, not worth more than that.
- The HTML `/sitemap/` page (not the XML sitemap) under-lists the blog collection — flagged as a minor, separate, one-line fix.
